# E20a — Signed, pinned authority checkpoints (single-host)

## What is implemented

`atlas.authority_checkpoint` makes a **read-only consistent SQLite/WAL snapshot** of the E16 `global_namespace` authority and a single trusted tenant's `entries` and `operations` tables. It hashes every ordered row using length-delimited canonical JSON, then emits a checkpoint signed with an independently pinned Ed25519 public key. Records are chained through SHA-256 and published with fsync and no-overwrite hard links. A private directory lock serializes append operations.

Every subsequent checkpoint requires an independently supplied hash pin of the preceding tip. Verification independently checks sequence, canonical structure, signatures, predecessor hashes, monotonic epoch/generation and operator-asserted time. `--match-current` compares the head against a new consistent database snapshot, detecting a restored, rewritten or otherwise diverging local state. Empty histories do not pass verification. The initial append uses the all-zero hash sentinel.

**Do not put the signer key, private audit directory and independently trusted tip together under the same mutable/compromised authority.** Keep the tip and verification public key on an independent offline device or integrity-protected external system. A locally stored plain text tip cannot defeat an administrator who can overwrite the database, audit files and pin. Signature timestamps are operator-supplied and not hardware-attested trusted time.

## Local usage

Create an Ed25519 key by your approved key management process (raw 32-byte private seed for this module, owner-only `0600`) and retain its independently verified raw 32-byte public key. The key is not auto-generated by a service. No environment-variable secrets are accepted.

```bash
umask 077
mkdir -m 700 -p /private/checkpoints
# Initial checkpoint; runs after a trusted E16 namespace transaction:
python3 -m atlas.authority_checkpoint --db /private/namespace/meta.sqlite \
  --dir /private/checkpoints --tenant omega append \
  --key /private/keys/checkpoint-signing.seed \
  --expected-tip "$(printf '%064d' 0)" --now "$TRUSTED_UNIX_SECONDS"
# Preserve the returned digest in a separate trusted medium, then verify:
python3 -m atlas.authority_checkpoint --db /private/namespace/meta.sqlite \
  --dir /private/checkpoints --tenant omega verify \
  --public-key "$PINNED_ED25519_PUBLIC_KEY_HEX" --tip "$EXTERNAL_TIP" \
  --match-current
```

Use the prior external tip for each further `append`. Before any restore or promotion, fail closed unless the verified tip and current namespace state agree. A checkpoint must be created only when namespace writes are quiescent, or the next normal write will make an earlier checkpoint differ from current state; E20b must integrate a transactional gate/journal with the authoritative mutation flow. Checkpoints intentionally include tombstones and idempotency receipts, not only active file names.

## Security and nonclaims

- Checkpoints are a **post-transaction observation**, not a transactional replication log; a crash between the E16 mutation and append leaves the previous tip valid but not current. The verifier will reject `--match-current` until an operator reconciles the new state.
- Local `flock` does not coordinate separate physical machines. E20b requires quorum-backed epoch ownership (etcd or equivalent), durable fencing and split-brain drills.
- Verifies metadata only; not physical E14/E15 ciphertext availability or SMB file-lock semantics. Restore and availability tests require independent actual storage providers and real devices.
- Parent directories and all files must be private and owned by the current OS user; symlinks, FIFO, noncanonical or oversized files are rejected. SQLite contents are streamed in bounded records; no entire database is read into a Python heap.
- A database writer with sufficient OS privileges can modify E16 between checkpoints. External tip preservation is an **operational precondition**, not enforced by this module.

## E21b tenant binding (2026-11-23)

On successful `verify`, the response includes `tenant`, derived from the *verified and signed* checkpoint record. Empty-history opt-in used only for the initial append reports `tenant: null`; it is never an accepted restore checkpoint. Consumers authorizing tenant-scoped restore must compare this signed tenant explicitly with the recovery permit tenant, even when no current SQLite snapshot is requested. This is not an ACL or a distributed tenant authority.
